# Importing existing infrastructure code

Status: draft, 2026-10-21; phase 2 built 2026-10-22; adopt (phase 3's switching shapes) built 2026-10-22; adopt in the viewer, and raw Azure and Google Cloud resources, built 2026-10-22. Builds on `profiles-and-compiler.md` §3.7 (`infra` kit), §4 (compiler) and §8.1 (OpenTofu overlays).

## Goal

`rhizo import tofu infra/prod` reads an existing OpenTofu/Terraform configuration and writes a rhizo diagram of it. Compiling that diagram again produces infrastructure code that is **functionally the same** as the original. People and agents can then see, review and change the infrastructure as a diagram, and every change goes back out as code.

## The contract

Functional equality is defined by OpenTofu itself, not by text:

> For any state the original configuration manages, `tofu plan` of the compiled bundle reports **No changes**. Address changes are allowed only as `moved` blocks, which plan as zero-change moves.

Two levels of proof, both automated:

| Level | Needs | Check |
|---|---|---|
| **L1, offline** (every import, every CI run) | providers downloaded; no cloud access | Plan the original and the compiled configuration against the **same empty state** with every provider mocked (`tofu test` with `mock_provider`, see `infra-cloud-neutral.md` §1), so data sources return the same values on both sides. Compare `planned_values` (types, mapped addresses, every known attribute) and the `configuration` expressions after normalizing addresses. They must be equal. |
| **L2, live** (on request, e.g. before adopting) | read access to the real state | `tofu plan` of the compiled bundle against the real backend. It must say *No changes* apart from declared `moved` blocks. |

**Lossless or it refuses.** Every resource, data source, module call, variable, output, local, provider block, backend and `moved`/`import` block must end up somewhere: either as a kit-typed node, or carried verbatim. The import report says, per construct, which way it went. If anything would be lost, the import fails and names it. L1 runs at the end of every import (`--verify` is the default), so a successful import is a verified one.

## How it reads the code

OpenTofu does the evaluation; rhizo does not reimplement HCL semantics.

1. Run `tofu init -backend=false` and `tofu plan -refresh=false -out` against an empty local state, then `tofu show -json` on the plan. The JSON has two things rhizo needs:
   - `configuration`: every block with its **expressions and references**, including module calls and the modules' own configurations;
   - `planned_values`: the expanded resources (`count`/`for_each` resolved) with their known attribute values.
2. The `.tf`/`.tofu` files are also read as text (via an HCL parser), but only to carry hard constructs verbatim. These are `dynamic` blocks, complex `locals`, functions over variables, and comments next to the blocks they belong to.

State is never read for the diagram itself. State holds secrets; it is used only by L2 and by the overlays of §8.1, with their allow-lists.

## How it maps

| Code | Diagram |
|---|---|
| A `terraform-aws-modules` module call rhizo's compiler also emits (vpc, s3-bucket, lambda, rds, sqs, sns, kms, dynamodb-table, apigateway-v2) | The kit type (`aws.vpc`, `aws.s3.bucket`, …). Arguments the kit models become props; all others become **passthrough attributes** on the node. |
| A raw resource with a kit type (`aws_s3_bucket` plus its satellites: versioning, public access block, encryption, lifecycle, policy) | One kit-typed node. Satellite resources fold into props. The node remembers it came from raw resources (`origin`, below). |
| Any other resource, data source or module | A generic `infra.resource` / `infra.module` node, labelled by its type, with all arguments verbatim. It is drawn, connectable and compiled back unchanged. |
| A reference between blocks (`aws_iam_policy` → bucket ARN, `subnet_ids = module.vpc.private_subnets`) | An edge. Data access becomes a `data` edge (with `access` when it can be read off the IAM statement), placement becomes containment (VPC ⊃ subnet ⊃ service), everything else a `dependency` edge. The actual expression stays in the node's passthrough attributes, so the edge is the view, not the source of truth. |
| Variables, outputs, locals, providers, backend, `moved`/`import` blocks | Kept on the `infra.environment` frame (variables and outputs as props, the rest verbatim). |
| Constructs too dynamic to map (`dynamic` blocks, `for_each` over computed locals) | Verbatim on the owning node; if there is no owner, in a residual block on the environment frame. The report counts them. |

**Remembering the original form.** Every imported node carries an `origin` prop: its address (`module.orders_db`, `aws_s3_bucket.receipts`) and its shape (`module:terraform-aws-modules/rds/aws@7.2.2`, `resources`). In **preserve mode** (the default for imported diagrams), the compiler emits each node in its original shape at its original address. A diagram you have not changed therefore compiles to the same resources at the same addresses, and L1 can compare one to one. A node you change is re-emitted from its props in the same shape. Switching a node to rhizo's own shape (e.g. raw resources → the pinned module) is an explicit action. The compiler then emits `moved` blocks, so L2 still shows no changes.

## Making it reliable

- **Corpus.** Hundreds of real configurations: the `examples/` of every terraform-aws-modules module, AWS samples, and anonymized user projects. CI imports each one, compiles, runs L1 and must be green on all of them. Two numbers are tracked per release:
  - round-trip success, which must stay at 100%;
  - semantic coverage, the share of resources that became kit types instead of generic nodes, which should grow.
- **Property tests.** Generated configurations (random resources and references) go import → compile → L1.
- **Idempotence.** Import, compile and import again: the second diagram must equal the first.
- **Diff-friendly output.** Import writes deterministic KDL (sorted, stable ids from addresses), so re-importing after a code change shows a small diagram diff.

## Phases

1. **Verbatim import with L1.** `infra.resource` / `infra.module` / passthrough for everything, `origin` with preserve mode, environment frame, edges from references, `rhizo import tofu` with `--verify`. Round trip at 100% on the corpus. Semantic coverage can still be low.
2. **Semantic folding (built, below).** Neutral types for the modules rhizo emits and the common raw resources of all three clouds and their satellites, containment, and `access` on data edges.
3. **Live.** L2 against real state, drift as an overlay (§8.1), and switching shapes with `moved` blocks (adopt: built, below; its live check is a person's step).
4. **More sources.** Other providers (Azure, Google), Terragrunt, and CDK for Terraform via its synthesized JSON.

## Phase 1 as built

`rhizo import tofu DIR -o FILE.rhizo` (crate `rhizo-iac`) and `rhizo verify-roundtrip DIR [--diagram FILE]`.

**Reading.** The `.tf`/`.tofu` files of `DIR` are parsed with `hcl-edit`, following OpenTofu's loading rules (`x.tofu` replaces `x.tf`). OpenTofu then plans a temporary copy offline: an override file sets a local backend, and a generated test file (`zz_rhizo_l1.tftest.hcl`, the only one run) mocks every provider except OpenTofu's built-in one, whose `terraform_remote_state` data sources are overridden (real, one fetches any URL or reads any local file), with defaults from the provider schema so mocked values pass validation (`crates/iac/src/mocks.rs`). No provider is configured, so nothing logs in, calls a cloud or runs a program through a provider (`external` is mocked too). The provider programs themselves still run: see "Security: which code runs". The process gets an allow-listed environment (no `AWS_PROFILE`, empty AWS config files, metadata service off). `configuration` of the plan must name nothing the parsed blocks lack, and gives the references that become edges. State files are never opened or copied.

**Storing expressions.** Every argument is kept as its HCL source text, a string in the node's `body` prop: `bucket = "x-${var.env}"` is stored as the string `"x-${var.env}"` *with* its quotes, `count = 2` as `2`. Inside `body` a string is always an expression; an array is the list of nested blocks named by its key (`rule`, `dynamic "ingress"`, labels quoted as in HCL). Nothing is re-interpreted, so heredocs, templates, `for` expressions and `dynamic` blocks survive unchanged. The key order of a body has no meaning (HCL's does not either, and the KDL form writes simple values first); the order of blocks of one type is kept.

**Types.** `infra.resource` (`tf-type`, `mode` = managed, data or ephemeral, `name`, `body`) and `infra.module` (`source` and `version` when they are literals, `name`, `body`). Both carry `origin` = { `address`, `shape`, `file` }. Badge: the resource type, or `MODULE`. They draw as plain boxes, take no part in the edge rules, and the brief lists them as generated (no tasks). The environment frame of an import has `origin` = { `dir` } instead of `region`, `blocks` (every other block, verbatim, with its file) and `lock-file` (`.terraform.lock.hcl` verbatim, the one hidden file a bundle may hold).

**Preserve mode.** An environment with `origin` compiles back as that root module: its `blocks` and its generic nodes, each into the file it came from (an override-file name or anything unsafe falls back to `main.tf`). A node whose `name` changed after the import also gets a `moved` block from its `origin.address`. Kit-typed nodes are an error in an imported environment, unless folded from its code (phase 2, below). Generic nodes in a designed environment compile into its `main.tf`.

**L1.** The diagram is compiled and its environment written to a second temporary folder (plus the original's `terraform.tfvars`/`*.auto.tfvars`, which are inputs and never imported). Two checks, both must be equal:

1. *Blocks.* Both folders are parsed the same way; every block (kind, labels, body with keys sorted) must appear on both sides as often, and the lock files must match. A difference names the block and the argument path.
2. *Plans.* Both are planned against an empty local state with the same mocked providers; `planned_values` (without its `outputs` map, which in `tofu test` plans also holds module outputs under colliding names), `resource_changes`, `output_changes` and `configuration` must be equal after sorting lists of addressed objects by address. Variable values are the same files on both sides; `configuration` covers variable declarations and `check` blocks. `import` blocks and state `encryption` blocks are cut from both sides before planning; check 1 still covers them.

**Refused** (the import fails and names them): override files, JSON configuration, local module sources, top-level arguments, an argument set twice, files that do not parse. Code that reads files outside the configuration (`file("policy.json")`) fails L1, because the bundle does not carry them. Comments are not carried; the report says so.

**Limits.** One root module per import; variables without a default need a `terraform.tfvars`; mock profiles exist for aws, azurerm and google (others are mocked plainly and may fail a provider's own validation, which names the attribute); a provider renamed in `required_providers` is not mocked under its local name yet. References through `locals` draw no edge.

**L1 on mocked providers (2026-10-22).** Fake credentials could not plan rhizo's own output (its pinned modules read `aws_caller_identity` and `aws_availability_zones`) nor Azure or Google code (those providers log in when configured). L1 now plans with `mock_provider`; see `infra-cloud-neutral.md` §1.

**Corpus** (`crates/iac/tests/corpus/`, run by `cargo test -p rhizo-iac -- --ignored`, skipped without `tofu`): an Azure storage setup, a Google storage setup, an S3 bucket with satellites and a lock file, a VPC module call, Lambda with IAM, `count`/`for_each`/aliased provider, `dynamic` blocks and complex locals, `moved`/`import`/`removed`/`check` with a `.tofu` file, plus rhizo's own `examples/shop` output. Each imports with L1 equal and re-imports from its compiled code to the same diagram.

## Phase 2 as built

Semantic folding, for all three clouds (`crates/kit/src/infra/fold.rs`, recognizers in `fold/{aws,azure,gcp}.rs`). The recognizers live in `rhizo-kit`, so the importer and the rules share them (`rhizo-compile` cannot depend on `rhizo-iac`).

**A folded node is a typed view of verbatim code.** The importer gives a recognized node a neutral type (`infra.bucket`, …) instead of `infra.resource`/`infra.module`. It keeps `tf-type`, `mode`, `name`, `source`, `version`, `body` and `origin` exactly as in phase 1, so preserve mode still compiles it verbatim and L1 stays equal on every corpus entry. It adds the **derived props**: the neutral props its *literal* arguments state, plus the cloud block for settings only one cloud has (`aws { instance-class }`, `azure { access-tier }`, `gcp { tier }`). Literals include objects and lists whose parts are all literal, `jsonencode(…)` of them, and templates without interpolation. An absent argument derives the provider's or module's default where the kit's default differs (an S3 bucket without a versioning resource is `versioning=#false`; a Lambda function without `timeout` is `timeout-s=3`). An expression derives nothing; a value out of the kit's range (5 GB of storage, a 90-day key deletion window) is not derived either. Both are counted in the report as "not read". The neutral schemas take the code props from one shared definition (`schemas/imported.json`, resolved by `$ref` within the kit), marked `readOnly`; `infra.subnet`'s `tier` and `infra.table`'s `partition-key` are required only without `origin`.

**Recognizers.** Per cloud, the raw resources and the modules rhizo emits:

| Neutral | AWS | Azure | Google Cloud |
|---|---|---|---|
| `infra.bucket` | `aws_s3_bucket` + versioning, lifecycle, encryption, public access block, policy, ownership controls; `s3-bucket` | `azurerm_storage_account` + management policy, containers, customer-managed key; `avm-res-storage-storageaccount` | `google_storage_bucket`; `cloud-storage//modules/simple_bucket` |
| `infra.queue` | `aws_sqs_queue`; `sqs` | `azurerm_servicebus_queue`; a namespace module with exactly one queue | `google_pubsub_subscription`; a `pubsub` module with one subscription named like its topic |
| `infra.topic` | `aws_sns_topic`; `sns` | `azurerm_servicebus_topic`; a namespace module with exactly one topic | `google_pubsub_topic`; any other `pubsub` module |
| `infra.key` | `aws_kms_key`; `kms` | `azurerm_key_vault_key` (its vault's soft-delete window); `avm-res-keyvault-vault` with one key | `google_kms_crypto_key`; `kms` with one key |
| `infra.function` | `aws_lambda_function`; `lambda` | `azurerm_function_app_flex_consumption`, `azurerm_linux_function_app`; `avm-res-web-site` with `kind = "functionapp"` | `google_cloudfunctions2_function` |
| `infra.table` | `aws_dynamodb_table`; `dynamodb-table` | `azurerm_cosmosdb_account` + SQL database and container; `avm-res-documentdb-databaseaccount` with one container | `google_firestore_database` + a TTL field |
| `infra.database` | `aws_db_instance` and `rds` with `engine = "postgres"` | `azurerm_postgresql_flexible_server` + database; `avm-res-dbforpostgresql-flexibleserver` | `google_sql_database_instance` (`POSTGRES_*`) + database; `sql-db//modules/postgresql` |
| `infra.network` / `infra.subnet` | `aws_vpc` (+ `aws_flow_log`), `aws_subnet`; `vpc` | `azurerm_virtual_network`, `azurerm_subnet`; `avm-res-network-virtualnetwork` | `google_compute_network`, `google_compute_subnetwork`; `network` |
| `infra.api` | `aws_apigatewayv2_api` (HTTP); `apigateway-v2` | `azurerm_api_management`; `avm-res-apimanagement-service` | `google_api_gateway_gateway` |

Everything else stays generic. **Satellites** (resources that configure one main resource and refer to it) fold their meaning into its props and stay nodes of their own, verbatim, joined to it by the dependency edge of their reference. An edge, not nesting: a satellite is a block at its own address, nesting would turn every bucket into a container (and the kit's `parents` would have to allow generic nodes inside neutral ones), and the reference edge is already there. The report names each satellite "folded into" its main node.

**Read-only props.** `[infra.import.derived]` (error) recomputes the fold of every kit-typed node in an imported environment and names each prop that differs from what its code says ("prop `versioning` is read-only: its code says false, the diagram says true"), with the fix: edit the HCL in `body`, or change the code and re-import. A node whose code folds to another type, or to none, is the same error. `sensitive` stays editable: it annotates the diagram, not the code. `[infra.import.kit-type]` still rejects kit-typed nodes without `origin` (and `aws.*` types) in imported environments; `[infra.import.code]` rejects code props on neutral nodes of designed environments, where they would be ignored.

**Audit.** Kit rules that fire on the nodes and edges of an imported environment become warnings prefixed `audit:`, with "this reports on the imported code" in their help; they never block compiling the code back. Folding adds two: `[infra.audit.versioning]` (a bucket without versioning) and `[infra.audit.public]` (an RDS instance with `publicly_accessible = true`, a flexible server with public network access, a Cloud SQL instance with a public IP). Rules that read code shape rather than meaning are skipped there: subnet tiers (imported subnets are per zone), database placement (a subnet group places it without a drawn edge), route checks (routes are in the API's code) and edges without kit meaning.

**Edges.** References with a generic end stay dependency edges. Between two folded nodes the edge gets the kind its `link()` implies, turned around when only the reverse has a meaning (a Pub/Sub subscription refers to its topic; the topic subscribes it): grant → data, route and trigger → control, subscribe → data to a queue and control to a function, place and encrypt → dependency. A Lambda module's `event_source_mapping` is a trigger; a read-only grant to the queue that triggers the function is the trigger's consume permission, not a grant edge of its own (since adopt). A generic block that refers to exactly two folded nodes with a link joins them (an event source mapping, an SNS subscription, an integration, an encryption satellite). **Grants** come from IAM: the function's identities (itself, an IAM role, a managed identity, a service account, or one entry of a service-accounts module) are matched with the blocks that grant to them or the policies it names; statements, role names, role definitions and bindings that name a store give `access`: actions and permissions by verb (consuming from a queue reads it), built-in Azure and predefined Google roles by name, custom roles by their permissions. Where nothing says it, `access` is unset and counted in the report ("data edges without access"). **Containment:** a subnet nests in the network it names; a function or database nests in the one subnet it names, or in the network when it names several subnets of one network or the network itself (`vpc_subnet_ids = module.net.private_subnets`).

**Cloud.** The environment's `cloud` is set from the providers its nodes use (aws, azurerm/azapi, google, by resource type or module source). With more than one, the majority wins and the report warns.

**Coverage** (the share of resources and module calls, not data sources, that folded or are satellites; `tests/corpus/README.md`, checked by `corpus_round_trips`): azure-storage 50 %, count-for-each 75 %, dynamic-locals 0 %, gcp-storage 50 %, lambda-iam 33 %, moved-import 67 %, s3-bucket 100 %, vpc-module 33 %; rhizo's own output 60 % (aws), 27 % (azure), 31 % (gcp): their identities, IAM, security groups, NAT, DNS and monitoring modules stay generic. Every entry still imports with L1 equal and re-imports idempotently.

**The full circle** (`rhizo_output_round_trips`, `azure_output_round_trips`, `gcp_output_round_trips`): rhizo's own output for each example, imported, gives back each source node as its neutral type at the address its id names, with the literal props the source wrote, apart from named gaps. aws (`examples/shop`): 9 of 11 nodes, 12 of 12 props; the two subnet tiers are inputs of the vpc module. azure (`12-azure-infra.rhizo`): 8 of 12 nodes, 15 of 20 props; the subnet tiers, the queue and topic sharing one Service Bus namespace module, NAT (its own module), flow logs (not compiled on azure), the function timeout (host.json), `memory-mb` (comes back as `azure.instance-memory-mb`) and the environment (edges add variables by reference). CORS is read from the API policy's `<allowed-origins>` (since adopt). gcp (`13-gcp-infra.rhizo`): 10 of 12 nodes, 21 of 27 props; the subnets and database tier, NAT, the handler (`main.handle` → entry point `handle`), the environment, the table's partition key (Firestore has none), the key's description and CORS. The tests assert exactly these gaps. The network's range comes back from its private subnet, the first /len+4 of it in rhizo's layout (since adopt).

**Next.** Switching a node to rhizo's own shape: built as adopt (below). Also: more recognizers as the corpus grows, `access` from resource policies, and placement through subnet groups.

## Adopt (switching shapes) as built

`rhizo adopt FILE NODE... [--all] [--dry-run] [--report F] [--var-file F]` switches folded nodes of an imported environment from their verbatim code to rhizo's own code (`crates/iac/src/adopt.rs`). Their props then stop being read-only: rhizo generates their code from the props, exactly as for designed nodes. `rhizo_iac::adopt` is itself a dry run: it returns the rewritten diagram and the report, and the caller writes; `--dry-run` prints the report and writes nothing. `--against OLD.rhizo` runs only the offline check of a later edit against an earlier version (writes nothing). Agents get the same as the MCP write tool `adopt_nodes` (listed only with `--allow-write`).

**In the viewer.** On a node of an imported environment the inspector shows a Code section: "Adopt…" when `rhizo_iac::adoptable` (the shape checks, no OpenTofu) passes, else the refusal itself; "rhizo's code (adopted)" afterwards. The palette has "Adopt node…" (the selection; the viewer selects one node at a time), "Adopt all that switch without changes" (`--all`) and "Cancel adopt". The dry run runs on a worker thread (`viewer/workers.rs`, `rhizo_app::adopt::Job`), one at a time; `Options` gained `progress` (the status bar shows "Adopting `x`… planning the original code") and `cancel` (the running `tofu` is killed, the run answers `Error::Cancelled`, nothing is written; switching files cancels too). Adopt reads the file as saved: the viewer writes every canvas edit at once and typing once it parses, so pending typing in the text pane is refused with a message (⌘S saves it), not saved behind the person's back. When the run ends the report waits in a modal dialog (moves, "adopting changes …", creates, the live-plan rule) with Adopt and Cancel buttons (⌘Enter, Esc; plain Enter does nothing). Adopt writes only if the file on disk is still the text the run read, as one editor edit: saved, shown in the text pane, one ⌘Z step; the inspector then edits the node's props like any other. `--all` whose result has no change and no create is written without the dialog. Verified headlessly: the job state machine, the dialog keys and palette rows (unit tests), cancellation against real OpenTofu (`adopt_reports_progress_and_cancels`), and the inspector button and report dialog drawn offscreen (`adopt_button_and_report_render`); clicking through the window is a person's check.

**The diagram.** Adopting rewrites the file in place with the format-keeping `Editor` (which gained lists and objects in `set_prop`, `set_frame_prop` and `set_edge_prop`). The node keeps its id, neutral type and props, and loses `tf-type`, `mode`, `name`, `source`, `version` and `body`. `origin` becomes what the compiler moves:

```kdl
node "receipts" id=aws_s3_bucket.receipts type=infra.bucket {
    props versioning=#true {
        origin address="aws_s3_bucket.receipts" shape="rhizo" {
            also "aws_s3_bucket_versioning.receipts" "aws_s3_bucket_policy.receipts" …
            keep bucket_prefix="\"${var.environment}-receipts-\"" tags="{\n    Name = \"receipts\"\n  }"
        }
    }
}
```

`shape "rhizo"` marks the node as rhizo's code. `address` and `also` (the satellites folded into it, whose nodes are removed with their edges) are where it came from; the compiler derives each `moved` target from the shape tables (`rhizo_kit::infra::adopt`), so the diagram never holds module-internal addresses that a later module pin could change. `keep` holds arguments carried verbatim as HCL because rhizo would write them differently and changing them renames or retags what exists: bucket, queue, topic, table, function and database names, tags and labels (rhizo derives names from the environment and node ids, which an import does not choose). `name` appears only when `module.<label>` is taken (`aws_kms_key.events` and `aws_sns_topic.events` become `module.events` and `module.events_topic`). One prop, not several: `origin` already is the read-only record of where code came from, and everything editable stays in the node's own props. Two more things move from code into the diagram where rhizo writes them from it: the node's label, from the argument rhizo writes the label into (a function's or API's `description`, API Management's `publisher_name`), and an API's routes, as the `route` prop of its edges (now one route or a list), read from the `routes` map (AWS) or the operations and their `set-backend-service` (Azure). References to a moved address in the code that stays (other nodes' bodies, outputs, locals) are rewritten through the module's outputs: `aws_s3_bucket.receipts.arn` → `module.receipts.s3_bucket_arn`, a bare address in `depends_on` → `module.receipts`. An attribute without an output, or one of an absorbed satellite, refuses the adopt, naming the block that reads it.

**Compiling.** The imported environment stays in preserve mode. Adopted nodes compile into `rhizo.tf` with the cloud's own emitter, run on a view of the environment in which adopted nodes, and nodes folded from module calls or from the resources rhizo's own code is (Google Cloud functions, Firestore databases, API gateways), go by their code's name (`module.orders_db` → `orders-db`). rhizo's references then resolve to what exists: `module.orders_db.db_instance_address`, `google_cloudfunctions2_function.worker`. From what the emitter writes for the node, only the blocks at its addresses are kept (`module.<name>`, `origin`, the satellites); kept arguments replace rhizo's (a kept `bucket` replaces `bucket_prefix`); a `moved` block follows for each address the code no longer has. The environment's provider configuration is the one the module calls use, as before. The emitters were factored per node (`node_groups`) for this; designed output is byte-identical (the baseline of every example). Code that was rhizo's already has rhizo's helpers verbatim (locals, identities, policy documents, security groups, variables) under rhizo's names, which the view makes rhizo's references find. **Helpers for code of another shape:** where the environment does not define a helper rhizo's code refers to, the compiler rewrites the reference to a `rhizo_` one and writes its definition at the top of `rhizo.tf`: on Google Cloud `local.project`, `local.region` and `local.suffix` become `local.rhizo_project` (the default `provider "google"` block's `project`), `local.rhizo_region` (its `region`) and `local.rhizo_suffix`; on Azure `data.azurerm_client_config.current` becomes `data.azurerm_client_config.rhizo_current` (a data block, no resource) and `local.tags` an empty map. Only helpers some adopted code still uses after `keep` are written; rhizo's own output imported defines them already and stays byte-identical. Any other missing reference is named by OpenTofu in L1-adopt, and the edge rule below names the edge. **`keep` by input:** a raw type's table entry can say where rhizo's module takes each kept argument (`name` of a `google_pubsub_topic` → `topic`, its `project` → `project_id`, the key ring's `name` → `keyring`, a key's `name` → `keys = [<name>]`, a key vault key's `name` → `keys.key.name`), so `origin.keep` is keyed by rhizo's input (a dotted path into an object input) and the values stay the original HCL. The offline harness also declares, in its override file, providers only a module requires (`Azure/azapi`, `Azure/modtm` of a Verified Module the root does not name), so they can be mocked.

**Rules.** `[infra.import.derived]` skips adopted nodes, `[infra.import.kit-type]` accepts them, and kit findings on adopted nodes and on edges touching one are full findings, errors included, not `audit:` warnings. Two new errors: `[infra.adopt.edge]`, a link whose adopted end's code refers to the other end as rhizo's code while that end is verbatim code of another shape (adopt both, or remove the edge); `[infra.adopt.satellite]`, a satellite left verbatim that rhizo's code now writes too (a lifecycle configuration once the adopted bucket has a `lifecycle` prop).

**Two levels of proof.** "No resource is replaced" cannot be proven offline: OpenTofu's `tofu test` has no `state_key` (Terraform has), so it cannot apply the original code with mocked providers and then plan the adopted code against that state, and real providers need credentials (Azure and Google log in, AWS data sources call the API).

| Level | When | Check |
|---|---|---|
| **L1-adopt, offline** | every adopt, before anything is written | The code before and after is compiled and planned with the mocked providers L1 uses, against an empty state. Each original managed instance is mapped through the `moved` blocks of `rhizo.tf` (an instance, `from[key]`, or something inside a moved module). Every one must be in the adopted plan, moved or at its own address; otherwise adopting refuses and names it ("would be destroyed"). Every attribute that differs per mapped instance is listed ("adopting changes …"), and every instance only the adopted code plans ("adopting creates …"). Mocks differ by address, so attributes the provider computes and neither code sets are not compared (counted); a value read from another instance's mocked attribute is equal when that instance is the one it pairs with, and otherwise listed as "reads X instead of Y". |
| **Live, a person's step** | before applying | The environment's apply task gets the criterion: `tofu plan` against the real state shows only these moves, the listed in-place updates and the listed creates; any replace or destroy is a stop. |

Only the live plan shows what a provider does with a listed change: whether it replaces the resource (a name rhizo would write differently, a module default such as `skip_destroy`), how it normalizes values (a key ARN against a key id), and the real values the mocks stand in for.

**`--all`** adopts every folded node that switches shape without a change: a node whose adopt would destroy, change or create anything in L1-adopt is left out and named, with what it would do ("adopt it by name to accept that"). Adopting by name accepts the listed changes.

**Cross-type moves on Azure** (checked 2026-10-22 against the sources, and reproduced with OpenTofu 1.13.2, azapi 2.13.0 and azurerm 4.81.0 against hand-made state): OpenTofu calls a provider's `MoveResourceState` for a `moved` block between types since 1.10 (`internal/tofu/node_resource_abstract.go`, `upgrade_resource_state.go`); `tofu validate` accepts such a block. azapi implements it only on `azapi_resource` (`internal/services/azapi_resource.go`, since 2.1.0), for any source type starting `azurerm`, from the source's `id` alone and without calling Azure: the moved state holds `id`, `name`, `parent_id` and the newest api-version, and the body only after a live refresh. Two things break it today: OpenTofu copies the azurerm resource identity onto the azapi object (the move request carries none), so plan fails with `attributes "id" and "type" are required` for every source type that has an identity (`azurerm_storage_account`, `azurerm_virtual_network`, `azurerm_subnet`, `azurerm_linux_function_app`); and a target address the module's own `moved` blocks also name (the storage account, a subnet's `[0]`) is an "Ambiguous move statements" error on every plan. `azapi_update_resource` (the storage module's customer-managed key) has no move at all. Mocked providers refuse moves in `tofu test` ("Moving is not supported in testing context"), so none of this is reachable offline. The Azure types adopted are those whose modules keep azurerm resources, where the moves stay within one type.

**Safety of what the offline plan cannot compare.** As for the S3 bucket policy, settings that grant or deny are taken over only when they are exactly what rhizo writes: a key vault must authorize with RBAC only (rhizo turns access policies off: their grants would end), have no access policies and no network rules narrower than rhizo's Allow; a Cloud Storage bucket must have uniform bucket-level access on already (rhizo turns it on, which ends every ACL grant, and ACLs are not in the plan) and, unless public access prevention is enforced already, nothing that grants to `allUsers` or `allAuthenticatedUsers`. Anything else is refused by name. IAM resources that grant on an adopted resource stay verbatim and keep granting.

**Provider versions.** Raw code of another shape compiles into modules pinned with rhizo's code, so its provider must fit them: on Google Cloud the environment's `required_providers` constraint must admit `hashicorp/google` 7.46.1 and its lock file must lock a 7.x; on Azure the constraint must admit `hashicorp/azurerm` 4.81.0 and the lock a version from 4.81 to below 5. Otherwise adopting refuses, naming the version ("this environment locks google 6.49.0"). Google code must also name a project, in the resource or the default provider block.

**Limits.** One imported environment per diagram. Nodes with `count`, `for_each`, `provider`, `depends_on`, `lifecycle` or `dynamic` blocks that rhizo's code would not write the same are refused by name, as are names rhizo's code cannot write (upper case). A satellite rhizo's code does not manage with the node's props stays verbatim (`[infra.adopt.satellite]` guards a later prop change). Variables without defaults need `--var-file`. Mocked values make some differences approximate, as above: the live plan decides. Policy documents are mocked data sources, so the offline plan cannot compare their contents: a raw bucket is adopted only when its bucket policy is the TLS-only document rhizo's code writes (one Deny statement on `aws:SecureTransport` from a policy document data source); any other bucket policy refuses by name, since adopting would replace its statements unseen.

## Security: which code runs

Importing (`rhizo import tofu`, `rhizo verify-roundtrip`) and adopting (`rhizo adopt`, the MCP tool `adopt_nodes`, the viewer's "Adopt node…") run OpenTofu on code that may come from anyone. What runs:

- **Providers run.** Every provider is mocked, but `tofu init` downloads each provider the code requires, in the root module or in any module it calls, and OpenTofu starts each one to read its schema (`tofu providers schema`, `tofu test`). A provider is a program from its publisher, running as you. So rhizo installs only an allow-list.
- **Module code does not run.** `tofu get` (and `init`) download module sources over the registry, git or HTTP. That is HCL, read by OpenTofu, not executed; git runs with your git configuration. Only providers execute, and a module's providers go through the same allow-list.
- **Nothing else.** No backend (a local one is forced), no state, no provisioners (nothing is applied), no credentials (an allow-listed environment).

**The allow-list** (`ALLOWED` in `crates/iac/src/providers.rs`): on `registry.opentofu.org`, `hashicorp/` `aws`, `azurerm`, `google`, `google-beta` (the clouds rhizo compiles to), `random`, `null`, `local`, `external`, `time`, `archive`, `tls`, `http` (HashiCorp's utility providers the modules rhizo emits require), and `azure/azapi`, `azure/modtm` (Microsoft's, required by the Azure Verified Modules rhizo emits). Named one by one, not `hashicorp/*`: the registry's `hashicorp` namespace also serves other publishers' programs under legacy names (`hashicorp/github` downloads `integrations/terraform-provider-github`, `hashicorp/cloudflare` Cloudflare's), and a resource type without `required_providers` implies one of those.

**Refused before download, by name.** Before `tofu init`, rhizo reads what the code requires: `terraform { required_providers }` of the root module (a local name without `source` is `hashicorp/<name>`), every provider in its lock file, and, when there are module calls, the `required_providers` of every module `tofu get` fetched (`.terraform/modules/modules.json`). Anything not allowed fails the run before any provider is installed, naming the provider, where it is required and how to allow it:

```
refusing to run OpenTofu: the code requires providers rhizo does not install by default
  - integrations/github, required by module.team (versions.tf, source "registry.opentofu.org/mineiros-io/team/github")
OpenTofu starts every provider the code requires, even mocked, and a provider is a program from its publisher that runs on this machine. Nothing was installed. If you trust it, allow it for one run: `--allow-provider integrations/github` (CLI, or when starting `rhizo mcp`) or "Allow and adopt" (viewer).
```

The lock file counts because of the plugin cache: OpenTofu uses a locked provider already in the cache without asking any installation source (`internal/providercache/installer.go`, "Global cache dir enabled and contains locked provider"), so its own filter below does not cover it. An unreadable lock file is refused.

**OpenTofu enforces it too.** Every `tofu` run gets rhizo's own CLI configuration file (`TF_CLI_CONFIG_FILE`, written in the run's temporary folder), never the person's: `provider_installation { direct { include = [<allow-list>] } }`, so `tofu init` installs nothing else from the registry ("not found in any of the search locations"). The person's configuration is not read because it may hold `dev_overrides` (a local program used as a provider), a filesystem mirror (any binary) or a network mirror. With `TF_CLI_CONFIG_FILE` set, OpenTofu reads that file only: not `~/.tofurc`, `~/.terraformrc` nor `~/.terraform.d/*.tfrc` (`internal/command/cliconfig/cliconfig.go`, `LoadConfig`: the config directory is skipped when the location is overridden), and an explicit `provider_installation` replaces the implicit local mirrors (`~/.terraform.d/plugins`, `terraform.d/plugins` in the working folder; `cmd/tofu/provider_source.go`). The environment is cleared and only `PATH`, `HOME`, temp, proxy and certificate variables pass, so neither `TF_CLI_ARGS`/`TF_CLI_ARGS_<command>` nor `TF_REATTACH_PROVIDERS` reach it; the plugin cache stays `TF_PLUGIN_CACHE_DIR`, set by rhizo. `GOOGLE_APPLICATION_CREDENTIALS` points at an empty file, so a `gcs::` module source cannot use the person's gcloud credentials (the AWS files are empty for `s3::` sources the same way). The temporary folders are private to the person (mode 0700): they hold the variable files. The temporary copy holds no `.terraform` folder.

**Every configuration mocked.** `tofu test` replaces a provider configuration with a `mock_provider` by the root module's local name, so rhizo writes one mock per provider type and one per local name the root module gives it (`ext = { source = "hashicorp/external" }` gets `mock_provider "ext"`). A configuration left real would run the provider during the "offline" plan (`external` runs programs). A `provider` block inside a module (legacy in-module configuration) cannot be mocked from the root, so a module with one, or with JSON configuration rhizo does not read, is refused after `tofu get` and before `tofu init`. The built-in provider stays real (modules read `terraform_data` outputs), so every `terraform_remote_state`, at the top level or in a `check` block, in the root module or any module, gets an `override_data` whose `outputs` hold what the code reads, as null leaves (`mocks::remote_state_overrides`). Real, it would fetch any URL, and its address can carry `file()` contents out. A file that names one but cannot be parsed is refused.

**Module sources stay in the folder.** A module source that is an absolute path (OpenTofu links it into `.terraform/modules`) or a `file://` URL (linked or cloned) is refused, in the root module before `tofu get` and in fetched modules after it.

**Consent, per run.** CLI: `--allow-provider NAMESPACE/NAME` (or `HOST/NAMESPACE/NAME`, repeatable, no wildcards) on `import tofu`, `verify-roundtrip` and `adopt`, which says on stderr what it allows. MCP: only the person allows providers, when starting the server (`rhizo mcp --allow-provider X`); `adopt_nodes` has no parameter for it, so a prompt-injected agent cannot add one (the security review of 2026-10-25 found that an agent-set list let it install any provider). Viewer: a refused adopt opens the report dialog with the refusal and an "Allow and adopt" button, which runs the same dry run again with those providers allowed; a provider found only in a module after that is refused again, and asked for again. Nothing persists: each run asks again. A project-level allow file is a possible follow-up.

**What remains.** The allowed providers are trusted programs: their publishers, and the registry that serves them (OpenTofu checks each package's checksum and its publisher's signature from the registry, so a compromised registry entry is not caught). Module sources fetched over git or HTTP are code from anywhere, but only OpenTofu reads them. OpenTofu itself, git and the person's git configuration run as usual.
